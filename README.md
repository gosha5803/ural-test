# Поиск автозапчастей и аналогов

Клиент к веб-сервису «Проценка» ([документация API](https://lk.favorit-parts.ru/static/wsprice.pdf)): двухэтапный подбор номенклатуры. Сначала по артикулу находим производителей, затем по выбранному производителю получаем саму деталь и её аналоги с ценой и остатком.

**Демо:** https://ural-test.netlify.app/

## Как проверить

| Артикул       | Что увидите                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------- |
| `0189`        | несколько производителей (ZEN, NGK/NTK, CAFFARO…)                                            |
| `7160500039S` | один производитель MEYLE, у которого больше 700 аналогов: видны скролл, сортировка и счётчик |
| `7260500039S` | «Ничего не найдено»                                                                          |

- **Сбой сети.** В DevTools → Network включите _Offline_.
- **Загрузка.** Включите _Slow 4G_, чтобы рассмотреть лоадеры.

## Функциональность

### Этап 1. Производители

- Поиск по артикулу запускается кнопкой «Найти» или клавишей Enter. Пустую строку отправить нельзя, пробелы по краям обрезаются.
- Результат — список уникальных производителей в виде кнопок с подписью «Производители».
- Состояния:
    - до поиска — подсказка, что нужно ввести артикул;
    - первая загрузка — спиннер «Ищем производителей…»;
    - повторный поиск — прежние бренды остаются на экране приглушёнными и неактивными, рядом спиннер. Интерфейс не «прыгает», а клик по бренду из старой выдачи не отправит запрос с новым артикулом;
    - пустой результат — «Ничего не найдено»;
    - ошибка API или сети — сообщение об ошибке.

### Этап 2. Деталь и аналоги

- Клик по бренду отправляет запрос `number + brand + analogues=on + info=on`.
- Таблица с колонками «Название / Производитель», «Цена», «Остаток».
- **Цена** — минимальная среди складов, где товар есть в наличии (`warehouses[].price` при `stock > 0`). Верхнеуровневое поле `price` документация API просит не использовать. Если товара нет ни на одном складе, в цене стоит «—».
- **Остаток** — `count`, суммарный по всем складам. Цена при этом — с одного, самого дешёвого склада, поэтому она выводится как «от 300,00 ₽»: так не создаётся впечатление, что весь остаток доступен по этой цене.
- **Невозвратные позиции** отмечены лейблом «Невозвратный». По документации признак `notRefund` бывает у самого товара (масла, жидкости) и у предложения конкретного склада. Лейбл ставится, если невозвратен товар или именно то предложение, чья цена показана. Если невозвратен другой, более дорогой склад, к показанной цене это не относится. При равной цене выбирается возвратное предложение.
- Состояния:
    - первая загрузка — спиннер;
    - смена бренда — прежняя таблица приглушена, над ней бежит полоска загрузки;
    - пустой результат — «Ничего не найдено»;
    - ошибка — сообщение об ошибке.

### Работа с API

- **Пустой ответ.** API сообщает «не найдено» не пустым массивом, а массивом с одной пустой позицией (`goodsID` из нулей). Такой ответ распознаётся и превращается в пустой результат.
- **Ошибки.** Ответ `{"error": ...}` может прийти и с не-2xx статусом, поэтому сначала читается тело ответа, а потом проверяется статус. Сбой сети и ответ, который не является JSON, обрабатываются отдельно.
- **Спецсимволы.** `number` и `brand` передаются через `encodeURIComponent` (например, `NGK/NTK`, `#`, `&`), как требует документация.

### Гонка запросов

Пользователь может быстро переключать бренды или запускать новый поиск, не дождавшись ответа. Ответы при этом приходят в произвольном порядке. Каждый вызов `createAsyncThunk` получает уникальный `meta.requestId`: slice запоминает id последнего запроса и игнорирует ответы устаревших. Поэтому на экране всегда результат последнего действия пользователя, а не того запроса, который ответил последним.

## Сверх задания

- **Внутренний скролл таблицы.** Приложение занимает высоту окна, прокручивается только таблица, шапка закреплена. Чтобы сменить производителя, не нужно прокручивать страницу обратно наверх. При смене бренда или сортировки прокрутка сбрасывается на начало.
- **Счётчик позиций** под таблицей.
- **Сортировка по цене и остатку.** Клики по заголовку переключают: по возрастанию → по убыванию → исходный порядок.
    - Искомая деталь (артикул + бренд) закреплена первой строкой с отметкой, сортируются только аналоги.
    - Позиции без цены всегда стоят в конце, при любом направлении сортировки.
    - Сортировка стабильная: при равных значениях сохраняется порядок API.
    - Сортируется копия, данные в сторе не меняются.

## Стек и архитектура

**Vite, React, Redux Toolkit, Bootstrap 5, JavaScript.**

Задание просит делать как можно проще, поэтому структура плоская: компоненты и один slice состояния, без лишних слоёв и библиотек.

```
src/
├── config.js              # единственное место чтения env
├── store/
│   ├── index.js           # configureStore
│   └── partsSlice.js      # запрос к API, thunks, reducers, селекторы
├── components/
│   ├── SearchForm.jsx     # поле артикула
│   ├── BrandList.jsx      # этап 1: производители
│   ├── OffersTable.jsx    # этап 2: таблица, сортировка
│   ├── Loader.jsx         # LoaderBar (полоска) и Spinner
│   └── ErrorAlert.jsx
├── App.jsx
└── main.jsx
```

- **В сторе — сырые ответы API.** Уникальные бренды и список аналогов вычисляются мемоизированными селекторами (`createSelector`). Отдельных преобразованных копий данных в сторе нет.
- **Состояние сортировки — в компоненте.** Это UI-состояние одной таблицы, больше оно никому не нужно.
- **Статусы запросов** вынесены в константу `STATUS`, у каждого этапа свои `status` и `error`. Ошибка или загрузка на этапе 2 не скрывает список брендов.

## Что я бы развивал дальше

Эти шаги сознательно не сделаны: для двух экранов они дали бы больше кода, чем пользы. Но в случае дальнейшего развития проекта, данные доработки имели бы смысл.

- **Слой `api/`.** Вынести `fetchGoods` из slice в отдельный модуль. Slice станет отвечать только за состояние, а запрос можно будет переиспользовать и мокать.
- **`shared/ui`.** Перенести туда лоадеры, `ErrorAlert` и таблицу, как только они понадобятся второму экрану.
- **Unit-тесты** (Vitest): reducers (в том числе отбрасывание устаревших ответов по `requestId`), селекторы и чистые функции — `bestOffer`, `sortRows`, распознавание пустого ответа.
- **TypeScript.** Описать типы ответа API и стора, чтобы ловить ошибки на этапе компиляции.
- **Отмена запросов** через `AbortController` (`signal` из `createAsyncThunk`) при новом поиске и уходе со страницы. Это следующий шаг после `requestId`: устаревший запрос не просто игнорируется, а перестаёт нагружать сеть.
- **Предложения по складам.** Сейчас строка — это товар с лучшей ценой. Каждый склад — отдельное предложение со своей ценой, остатком, сроком отгрузки и возвратностью. Их можно показывать в раскрывающейся строке.
- **Виртуализация строк** (например, `react-window`), если выдача вырастет до тысяч позиций. Сейчас 700+ строк рендерятся без заметных задержек.
- **Состояние в URL** (артикул, бренд, сортировка), чтобы результатом поиска можно было поделиться ссылкой.
